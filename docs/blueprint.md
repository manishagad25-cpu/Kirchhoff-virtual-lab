# Vanilla TypeScript Template Blueprint

> **Agent action required:** Read `docs/agents.md` now and create `submission.md` in the project root if it does not exist.

This project is a CreatorEngine runtime wrapped in a minimal TypeScript + Vite application. Use this document as the context anchor before making code changes, especially when working with an agentic AI assistant.

## 1. High-Level Mental Model

The project has two halves:

- Editor-authored content: `project.bjseditor`, `assets/`, and scripts attached to scene objects.
- Vanilla runtime: `index.html`, `src/main.ts`, `src/App.ts`, Babylon.js engine setup, `loadScene`, `scriptsMap`, and generated `public/scene`.

Scene composition belongs in the editor side. Application shell, DOM UI, overlays, deployment, and browser integration belong in the Vite side. Gameplay or object behavior should usually live in `src/scripts/**` so it can stay attached to editor objects.

## 3. File Responsibilities

1. `project.bjseditor`
   - Editor manifest and project identity.
   - Stores package manager, plugins, texture settings, and last opened scene.

2. `assets/`
   - Source-of-truth authoring folder for editor scenes and assets.
   - Prefer editor-driven scene composition over hand-editing serialized scene files.

3. `public/scene/`
   - Generated runtime output.
   - Created by CreatorEngine or `yarn generate`.
   - Do not use it as a source folder for durable changes.

4. `index.html`
   - Browser HTML shell.
   - Must keep the canvas expected by `src/App.ts`.

5. `src/main.ts`
   - DOM bootstrap.
   - Creates the `App` after `DOMContentLoaded`.

6. `src/App.ts`
   - Babylon.js runtime class.
   - Owns canvas lookup, engine, scene, physics, loading, render loop, and disposal.

7. `src/style.css`
   - Global styling and canvas layout.

8. `src/scripts.ts`
   - Generated script map from editor-attached script paths to modules.

9. `src/scripts/**`
   - Scene-object behavior scripts.
   - Best place for gameplay, interaction, animation, and inspector-visible values.

10. `vite.config.ts`
   - Vite configuration.
   - Also excludes `@babylonjs/havok` from dependency optimization.

## 4. Runtime Entry Point

The DOM bootstrap starts in `src/main.ts`, which creates `new App()` after `DOMContentLoaded`.

The Babylon.js runtime lives in `src/App.ts`.

Key responsibilities:

- Find the `#canvas` element from `index.html`.
- Create the `Engine`.
- Create the `Scene`.
- Enable Havok physics.
- Load the generated scene with `loadScene("/scene/", "example.babylon", scene, scriptsMap, { quality: "high" })`.
- Attach the active camera controls.
- Start `engine.runRenderLoop`.
- Provide `dispose()` for scene and engine cleanup.

This is the smallest template. Prefer keeping framework-like abstractions out unless the user explicitly wants them.

## 5. Editor Contract

`project.bjseditor` lets CreatorEngine recognize this folder as an editor project. It points at the current authoring scene in `assets/example.scene`.

`assets/` is the source of truth for editor-authored content.

`public/scene/` is generated runtime output. Do not hand-edit it for lasting changes.

`src/scripts.ts` is generated and maps editor-attached scripts to imports. Add or edit behavior in `src/scripts/**`, then regenerate.

## 6. Runtime Loading Contract

The runtime loading contract is:

1. Wait for `DOMContentLoaded`.
2. Find `canvas#canvas`.
3. Create a Babylon.js `Engine`.
4. Create a Babylon.js `Scene`.
5. Enable Havok physics.
6. Keep side-effect imports for serialized editor content.
7. Call `loadScene("/scene/", "example.babylon", scene, scriptsMap, { quality: "high" })`.
8. Attach active camera controls after scene load.
9. Start exactly one render loop.
10. Keep disposal available through `App.dispose()`.

If an agent changes any step, it should test with `yarn dev` and `yarn build`.

## 7. Scripts And Scene Behavior

Use `src/scripts/**` for behavior attached to scene objects.

The default example script is `src/scripts/box.ts`. It implements `IScript` from `babylonjs-editor-tools` and rotates a mesh during `onUpdate`.

If a new script is added by code, it still needs to be attached to an object in CreatorEngine or included in the generated script map before it will run.

Script lifecycle guidelines:

1. Use constructors to receive the Babylon.js object passed by the editor.
2. Use `onStart` for initialization.
3. Use `onUpdate` for per-frame logic.
4. Use animation ratio or delta time for consistent motion.
5. Use editor decorators for inspector-tunable values.
6. Keep DOM UI code separate from object scripts unless intentionally bridged.

## 8. XR, VR, MR, AR, And Immersive Features

If the user asks for XR, VR, MR, AR, mixed reality, virtual reality, headset support, passthrough, hand tracking, spatial input, immersive mode, or Meta Quest support, use the Meta/Facebook Immersive Web SDK dependency declared as `@iwsdk/core`.

Agent rules for immersive requests:

1. Keep Babylon.js as the scene, rendering, asset, physics, and editor-content layer.
2. Use `@iwsdk/core` as the preferred immersive platform integration layer.
3. Do not invent a separate XR framework unless the user explicitly asks for one.
4. Preserve `loadScene` and `scriptsMap`.
5. Preserve `@babylonjs/core/XR/features/WebXRDepthSensing` unless a verified SDK integration replaces it.
6. Initialize immersive support after the engine, scene, and camera exist.
7. Put scene-object immersive behavior in `src/scripts/**`.
8. Put app-level session controls in DOM UI or a small runtime module.
9. If exact `@iwsdk/core` APIs are unknown, inspect installed package docs or types after dependencies are installed before coding.
10. Keep desktop fallback rendering working.

Recommended immersive implementation path:

1. Confirm `@iwsdk/core` is installed from `package.json`.
2. Inspect local SDK docs or types.
3. Add a small immersive adapter module.
4. Initialize it from `src/App.ts` after scene load.
5. Keep normal canvas rendering working.

## 9. Commands

Run these from this template folder:

```bash
yarn dev
yarn generate
yarn build
yarn serve
```

- `yarn dev`: starts the Vite development server.
- `yarn generate`: runs `babylonjs-editor-cli pack` and creates or updates `public/scene`.
- `yarn build`: builds the app.
- `yarn serve`: previews the built app.

Always run `yarn generate` before `yarn build` when scene assets or editor scripts changed.

- `package.json`

- `src/main.ts`
- `src/App.ts`
- `src/scripts.ts`

- Babylon.js side-effect imports that register loaders, cameras, materials, shadows, physics, and texture support.

Avoid:

- Editing `public/scene` by hand.
- Treating `src/scripts.ts` as normal application code.
- Adding a UI framework unless the task asks for one.
- Removing imports only because they appear unused.
- Implementing XR, VR, MR, or AR by bypassing the declared Immersive Web SDK dependency.

## 11. Common Changes

Add gameplay:

1. Add code in `src/scripts/**`.
2. Attach the script in CreatorEngine.
3. Run `yarn generate`.
4. Test with `yarn dev`.

Add DOM UI:

1. Keep `#canvas` present and stable.
2. Add controls in `index.html` or create them from TypeScript.
3. Keep resize handling so `engine.resize()` runs.

Change hosting base:

1. Check `vite.config.ts`.
2. Verify `loadScene("/scene/", ...)` still resolves to generated assets.
3. Build and preview with `yarn serve`.

Add immersive mode:

1. Keep `src/App.ts` responsible for browser-only setup.
2. Inspect `@iwsdk/core` local types or docs after install.
3. Create a small immersive adapter.
4. Connect it after the Babylon.js scene and camera are ready.
5. Preserve normal canvas rendering.

## 12. Master Blueprint For AI And Human Development

This section is the master prompt for building inside this template. Read it before adding features, generating code, or asking an AI agent to modify the project.

### 12.1 Project Intent

Every project should start with a short intent block.

Fill this in before major work:

1. Project type:
   - Game
   - Simulation
   - Tool
   - Interactive experience
   - XR, VR, MR, or AR experience

2. Core idea:
   - What is the user trying to do?
   - What is the world or scene about?
   - What is the most important interaction?

3. Target platform:
   - Web browser
   - Desktop browser
   - Mobile browser
   - Meta Quest or headset browser

4. Primary user:
   - Player
   - Designer
   - Viewer
   - Operator
   - Learner

5. Success condition:
   - What should feel good when the feature works?
   - What should the user be able to repeat?
   - What should be visible, measurable, or interactive?

Agent instruction: if the project intent is missing, infer the smallest reasonable intent from the user request and keep the project easy to redirect.

### 12.2 Core Interaction Loop

Define the repeated loop before implementing features.

Use this format:

1. User does an action.
2. Input layer receives it.
3. A system interprets it.
4. One or more entities change.
5. The scene renders feedback.
6. UI communicates state if needed.
7. The user decides the next action.

Example:

1. User presses movement keys.
2. Input system records direction.
3. Movement system computes velocity.
4. Player entity moves.
5. Camera follows or scene updates.
6. UI updates stamina or speed if present.

Agent instruction: do not implement a feature until its loop is clear enough to identify input, system, entity, scene feedback, and UI feedback.

### 12.3 Constraints

Document constraints early.

1. Performance target:
   - Default target is 60 FPS on a modern desktop browser.
   - For headset or immersive work, prefer stable frame time over visual complexity.
   - Avoid expensive per-frame allocations.

2. Scope:
   - Keep prototypes small.
   - Build thin vertical slices before broad systems.
   - Prefer one working interaction over many partial interactions.

3. Runtime:
   - This template runs in a browser through Vite.
   - Babylon.js rendering starts after `DOMContentLoaded`.
   - Keep the runtime simple unless the user asks for a framework.

4. Offline or backend:
   - Do not add a backend unless requested.
   - Prefer local state for prototypes.
   - Keep save or sync features isolated behind service modules.

5. Asset constraints:
   - Editor-authored scene assets belong in `assets/`.
   - Generated runtime assets belong in `public/scene/`.
   - Do not hand-edit generated scene output for permanent changes.

### 12.4 Non-Goals

Write non-goals to prevent feature creep.

Common non-goals:

1. Do not rebuild the CreatorEngine inside the runtime app.
2. Do not replace editor scene loading unless explicitly requested.
3. Do not create a new engine abstraction before there are multiple real use cases.
4. Do not add multiplayer, persistence, auth, payments, or backend systems unless requested.
5. Do not mix all feature logic into `src/App.ts`.
6. Do not add XR, VR, MR, or AR with a random library when `@iwsdk/core` is declared for immersive work.
7. Do not add a UI framework unless the user asks for one.

Agent instruction: when a request implies a non-goal, call it out and choose the smaller implementation unless the user confirms the larger scope.

### 12.5 System Mental Model

Think in layers:

1. Scene layer:
   - Babylon.js engine.
   - Babylon.js scene.
   - Camera.
   - Lights.
   - Render loop.
   - Environment and post-processing.

2. Entity layer:
   - Meshes.
   - Cameras.
   - Lights.
   - Transform nodes.
   - Particles.
   - Scene objects authored in the editor.

3. Systems layer:
   - Movement.
   - Input.
   - Interaction.
   - Collision responses.
   - Spawning.
   - Scoring.
   - State transitions.
   - XR session coordination.

4. UI layer:
   - DOM elements.
   - HUD.
   - Menus.
   - Buttons.
   - Debug panels.
   - Session prompts.

5. Integration layer:
   - `loadScene`.
   - `scriptsMap`.
   - `babylonjs-editor-tools`.
   - `@iwsdk/core` for immersive requests.
   - Vite build configuration.

Rule: keep responsibilities separate. A scene should not become a giant gameplay manager. A UI module should not directly mutate many meshes. A script should not secretly own global application routing.

### 12.6 Data Flow

Use this default flow:

1. User input occurs.
2. UI or input module captures it.
3. System reads input and current state.
4. System updates entities.
5. Entities affect scene transforms, materials, animations, or metadata.
6. Scene renders.
7. UI reflects important state.

For editor-attached scripts:

1. Editor attaches script to object.
2. `yarn generate` updates `src/scripts.ts`.
3. Runtime loads scene with `loadScene`.
4. `babylonjs-editor-tools` applies scripts from `scriptsMap`.
5. Script lifecycle methods run.

Agent instruction: preserve this flow unless the user asks for a different architecture.

### 12.7 Feature Thinking Process

4. What data does it need?

### 12.9 AI Output Requirements

AI-generated code should:

1. Be modular.
2. Avoid giant files.
3. Respect this template structure.
4. Preserve `loadScene`.
5. Preserve `scriptsMap`.
6. Avoid global mutable state unless clearly justified.
7. Include short comments only where useful.
8. Dispose Babylon.js resources when owning them.
9. Avoid unnecessary per-frame allocations.
10. Keep UI code in DOM-focused modules.
11. Keep scene object behavior in `src/scripts/**`.
12. Use `@iwsdk/core` for immersive features.

Reject or revise AI output that:

1. Replaces the project architecture without being asked.

### 12.10 Step-By-Step Development Flow

Use this loop for every feature:

1. Define the feature, desired behavior, and out-of-scope work.
2. Place it in scene, entity, system, UI, or integration.
3. Generate the smallest modular implementation.
4. Integrate it with scene, script map, UI, or system registry.
5. Attach scripts in the editor when needed.
6. Run `yarn generate` after editor asset or script attachment changes.
7. Test with `yarn dev`.
8. Check console and terminal errors.
9. Improve only after behavior works.
10. Build with `yarn build` for structural changes.

### 12.11 System Design Pattern

Every reusable feature should be describable as a system.

System template:

```text
Name:
Purpose:
Layer:
Inputs:
Outputs:
Entities affected:
Dependencies:
Update frequency:
Failure behavior:
Test plan:
```

Agent instruction: for multi-file features, write the system template first in implementation notes or comments.

### 12.12 Entity Design Pattern

Entities are objects in the world.

Guidelines:

1. Keep entities reusable.
2. Keep identity and state close to the object.
3. Avoid embedding broad game rules directly in entities.
4. Attach behavior through editor scripts or systems.
5. Prefer composition over deep inheritance.
6. Name entities clearly in the editor.
7. Keep units and scale consistent.

Entity checklist:

1. What is this object?
2. Who owns it?
3. What scripts are attached?
4. What systems read or modify it?
5. What happens when it is disposed?

### 12.13 Scene Responsibilities

The scene runtime should only:

1. Initialize engine.
2. Initialize scene.
3. Configure physics.
4. Load editor scene.
5. Attach camera controls.
6. Start render loop.
7. Register high-level services only when needed.
8. Clean up resources.

The scene runtime should not contain all gameplay logic, own all UI state, hard-code many unrelated object names, replace editor content casually, or create multiple render loops.

### 12.14 UI Responsibilities

DOM UI should:

1. Display state.
2. Collect user intent.
3. Provide HUD, menus, buttons, panels, and prompts.
4. Start or stop app-level modes.
5. Request immersive sessions when needed.

DOM UI should not own the Babylon.js render loop or hide scene lifecycle side effects in unrelated modules.

### 12.15 Immersive Feature Enforcement

For XR, VR, MR, AR, and immersive requests:

1. Use `@iwsdk/core`.
2. Keep Babylon.js as rendering and scene layer.
3. Keep editor loading through `loadScene`.
4. Keep `scriptsMap` intact.
5. Keep desktop fallback.
6. Isolate SDK calls in an adapter.
7. Initialize only after browser APIs are available.
8. Keep permission and session UI in DOM UI.
9. Put object-level immersive responses in scripts.
10. Verify device support before assuming headset behavior.

If an AI agent tries to use another immersive library, it must first explain why `@iwsdk/core` is insufficient.

### 12.16 Testing Mindset

After every change:

1. Check browser console errors.
2. Check terminal errors.
3. Confirm the scene still loads.
4. Confirm camera controls still work.
5. Confirm scripts still run.
6. Confirm UI does not block canvas input unintentionally.
7. Confirm performance remains acceptable.
8. Confirm generated assets are up to date when needed.
9. Confirm build still works for structural changes.
10. Confirm fallback behavior for unsupported devices.

### 12.17 Performance Awareness

Performance rules:

1. Avoid allocations in `onUpdate`.
2. Reuse vectors, quaternions, and matrices where practical.
3. Dispose resources when owned.
4. Avoid unbounded event listeners.
5. Avoid unnecessary raycasts every frame.
6. Avoid expensive material changes every frame.
7. Use instances or thin instances for repeated meshes where appropriate.
8. Keep physics bodies reasonable.
9. Prefer simple collision shapes.
10. Measure before complex optimization.

### 12.18 Extension Points

Add features in these places:

1. Scene object behavior: `src/scripts/**`.
2. DOM UI: `index.html`, `src/style.css`, or small TypeScript modules.
3. Runtime scene loading: `src/App.ts`.
4. Shared helpers: small modules under `src/`.
5. Immersive integration: adapter using `@iwsdk/core`.
6. Assets: source assets under `assets/` through editor workflow.

### 12.19 Common Mistakes To Avoid

Avoid:

1. Mixing all logic in one file.
2. Editing generated scene output by hand.
3. Forgetting `yarn generate`.
4. Removing side-effect imports.
5. Adding a framework unnecessarily.
6. Creating multiple engines for one canvas.
7. Creating multiple render loops accidentally.
8. Ignoring cleanup.
9. Adding globals for convenience.
10. Overbuilding systems before the interaction works.
11. Ignoring frame time.
12. Blindly trusting AI output.
13. Bypassing `@iwsdk/core` for immersive work.

## 13. Troubleshooting

- `Canvas element not found`: check that `index.html` still contains the expected `canvas#canvas`.
- Blank scene: run `yarn generate` and verify `public/scene/example.babylon` exists.
- Script not running: confirm it is attached in the editor and present in `src/scripts.ts`.
- Scene works in dev but not preview: check the Vite base path and `loadScene` root URL.
- Missing materials, lights, shadows, or textures: check Babylon.js side-effect imports in `src/App.ts`.
- XR request got implemented with unrelated APIs: revise to use `@iwsdk/core` as the integration layer.
